# 系统架构设计

## 一、总体架构

系统采用「客户端 — 边缘 / 服务端 — 数据与实时底座 — 外部模型」四层分层架构，各层职责单一、契约清晰，自上而下依赖、不反向耦合。

最上层是**客户端层**，由 Next.js 承载，包含主页与设计页两个界面，以及画布引擎（React Flow）、对话面板、状态管理与 Supabase 客户端。客户端负责一切呈现与本地交互，并通过两条通道与后端通信：对常规数据的增删改查走 Supabase 的 PostgREST 自动接口（在行级安全约束下直连数据库），对需要密钥、需要编排、需要服务端权限的敏感操作走 Edge Functions。

第二层是**边缘 / 服务端层**，由 Supabase Edge Functions 构成，是一组运行在 Deno 运行时、全球分布、按需启动的无服务器函数。它承担三类不可下放到客户端的职责：调用外部模型 API（持有密钥）、编排智能体的多步生成、以及对生成落库等需要服务端可信上下文的写操作。它是客户端与外部模型之间的唯一受信桥梁。

第三层是**数据与实时底座**，即 Supabase 的核心服务集合：PostgreSQL 数据库（持久化用户、项目、画布节点与边、会话、消息、生成任务、资产、模型目录）、Auth（鉴权与用户身份）、Storage（媒体对象存储）、Realtime（实时变更推送）、以及 pg_cron、Database Webhooks、Supabase Queues 等数据库原生能力。这一层是系统的真相之源（source of truth），所有状态最终都沉淀于此，并通过 Realtime 把变化反向推回客户端。

最底层是**外部模型层**，即 OpenAI、Google、火山方舟（Volcengine Ark）等模型提供商，以及 fal.ai、Replicate 等聚合平台。它们只被边缘层调用，对客户端完全不可见。系统通过「模型适配器」把它们各异的接口归一化为统一语义。

四层之间的协作可以用一句话概括：客户端发起意图，边缘层在持有密钥与服务端权限的前提下编排并调用外部模型，结果落入数据与实时底座，底座再把变化通过 Realtime 实时推回客户端，形成「意图下行、结果上行」的闭环。

## 二、前端架构

前端以 Next.js App Router 组织，核心原则是「能在服务端直出的就直出，必须在客户端运行的才下放到客户端」。

主页是一个「服务端外壳 + 局部客户端交互」的复合界面。页面骨架、用户信息与「最近项目」列表在服务端组件中借助带用户会话的 Supabase 服务端客户端直接查询并渲染，保证首屏快、数据新、对爬虫友好；而对话输入框、模型选择条、卡片悬停操作等需要交互的部分以客户端组件实现，嵌入服务端外壳之中。发起创作这一动作走服务端动作（Server Action）或一次 Edge Function 调用，完成「建项目 + 记首条消息」后重定向到设计页。

设计页则相反，是一个「客户端为主」的界面。画布与对话面板都高度依赖浏览器交互（拖拽、缩放、流式渲染、实时订阅），因此整体作为客户端组件运行；页面进入时通过一次服务端数据加载取得项目、画布节点与边、会话历史等初始数据作为水合（hydration）输入，之后的一切变更都在客户端发生，并经由 PostgREST 写回、经由 Realtime 同步。

前端内部以分层组织代码：呈现层是按界面与领域划分的 React 组件（画布相关、对话相关、主页相关、通用 UI）；状态层以轻量状态库（如 Zustand）维护画布状态（节点、边、视口、选择集、当前工具）与对话状态（消息流、流式缓冲），并负责本地乐观更新与远端同步的协调；数据层封装 Supabase 客户端、Edge Function 调用、Realtime 订阅与媒体上传，向上提供领域化的数据读写钩子（hooks）。这一分层确保画布交互的高频本地状态与后端的持久状态解耦：本地状态追求即时响应，持久状态追求最终一致，二者通过「乐观更新 + 防抖持久化 + 实时回流校正」三段式衔接。

## 三、Supabase 后端架构

后端不自建应用服务器，而是把 Supabase 的各项托管能力组合成一个完整后端，团队只需编写少量 Edge Functions 与数据库逻辑。

**数据库（PostgreSQL）**是核心。它不仅是存储，还通过行级安全（RLS）把「谁能读写哪行」这一鉴权逻辑下沉到数据库层，使得客户端可以安全地经 PostgREST 直连数据库做常规读写而无需中间业务层；通过数据库函数与触发器承载如「更新时间自动维护」「注册时自动建档」等贴近数据的业务逻辑；通过 pg_cron 跑定时任务（轮询异步生成任务）；通过 Database Webhooks 在特定行变更时回调 Edge Function；通过 Supabase Queues 为生成任务提供持久、可靠投递的队列。

**Auth** 提供用户身份与会话。它基于 JWT，签发的令牌既用于客户端访问 PostgREST 与 Storage 时的 RLS 上下文，也用于 Edge Function 校验调用者身份。支持邮箱密码、魔法链接与第三方 OAuth 登录；用户注册时通过触发器在业务表中为其建立档案。

**Storage** 存储一切媒体对象：用户头像、上传的参考图与素材、生成的图片与视频。它以 S3 为底、与数据库 RLS 打通，可按用户隔离访问权限，支持图片即时变换（生成缩略图）、签名 URL（临时授权访问私有对象）与 CDN 加速。

**Realtime** 是「结果上行」的关键。客户端按项目订阅频道，监听该项目下画布节点 / 边的行变更与生成任务的状态变更；当 Edge Function 把生成结果落库、或另一设备修改了画布，Realtime 把变化以毫秒级推送到所有订阅该项目的客户端，驱动画布即时更新。它同时提供广播（在连接用户间直接传递瞬时消息）与在线状态（presence）能力，为未来的协作留出空间。

**Edge Functions** 承担前述「不可下放」的逻辑。它们运行在贴近用户的边缘节点，以 V8 隔离实例按请求启动，持有外部模型密钥等机密（存于函数环境变量 / Supabase Vault），并以服务角色（service role）在必要时绕过 RLS 执行可信写入。

## 四、AI 服务层架构

AI 能力被组织为一个独立的服务层，横跨边缘层与外部模型层，核心是「模型适配器」抽象与「生成流水线」编排，详见第 05 篇，此处给出架构定位。

适配器层把每个外部模型 / 提供商封装为一个实现统一接口的适配器，对上暴露三组语义——提交一次生成、查询一次生成的状态、把提供商各异的返回归一化为统一的资产描述。同步型模型（多数图像模型）在一次调用内返回结果；异步型模型（视频、长任务）则返回外部任务号，需后续轮询或等待回调。

编排层在 Edge Function 中运行，负责把一次用户意图翻译为对适配器的一次或多次调用：在「纯生成」模式下它直接按所选模型提交生成；在「智能体」模式下它先理解意图、再决定调用哪些能力（生成图、生成视频、以参考图编辑、在画布上排布多个结果），可能形成多步骤序列。`@` 提及的画布元素被解析为参考素材一并传入。

异步任务的状态推进由「队列 + 定时轮询 + 回调」协同完成：提交后任务进入持久队列并落库为待处理；pg_cron 定时触发轮询型 Edge Function 拉取运行中的任务、向提供商查询进度、回写状态；若提供商支持回调，则由回调型 Edge Function 直接接收完成通知。任务一旦完成，结果资产入 Storage、生成记录置为成功、并在画布上创建对应节点；这一系列写入触发 Realtime 把结果推回客户端。

## 五、实时协同机制

系统的实时性建立在 Supabase Realtime 之上，围绕「项目」这一粒度组织。客户端进入设计页时，订阅以项目标识命名的频道，监听三类事件：画布节点表的行变更（插入 / 更新 / 删除）、画布边表的行变更、以及生成任务表中本项目相关任务的状态变更。

实时回流解决两个问题。其一是**生成结果的异步落地**：用户发起生成后无需轮询，结果就绪时由 Realtime 主动推达，画布上的占位节点据此替换为真实内容。其二是**跨设备 / 多标签页一致**：同一用户在多处打开同一项目时，任一处的编辑都会经数据库变更被广播到其余处，保持画布一致。

并发写入采用「按节点为粒度的最后写入胜出（last-write-wins per node）」策略：每个节点的变更独立提交，节点上携带更新时间戳，远端回流的变更若比本地版本新则覆盖本地。由于本产品当前不开启多人实时协作（不在范围内），冲突主要来自同一用户的多设备，按节点粒度的最后写入胜出已足够；若未来引入多人协作，可在此基础上叠加 CRDT 或操作变换以处理细粒度并发，这是预留的演进方向而非当前设计内容。

客户端本地的高频交互（拖动过程中的连续位移、缩放过程中的连续尺寸变化）不逐帧写库，而是先在本地状态中即时反映，待交互结束或防抖窗口到期后再把最终值持久化，从而既保证手感、又避免写入风暴。

## 六、关键数据流

**创建项目并发起首次生成**：客户端在主页提交想法与所选模型 → 经服务端动作或 Edge Function 创建项目行、创建该项目的会话与首条用户消息、并按所选模型创建一条待处理的生成任务 → 重定向到设计页 → 设计页加载项目、画布（此时为空或仅含占位）、会话历史，并订阅项目频道 → 生成任务由队列与轮询 / 回调推进，完成后落资产、建画布节点 → Realtime 把新节点推达，画布渲染出首批结果。

**对话中追加一次生成**：客户端在对话输入框提交指令（可含 `@` 提及与附件）→ 调用提交生成的 Edge Function → 函数创建生成任务、在画布上创建占位节点、把任务入队 → 返回后客户端立即显示对话进行态与画布占位 → 任务推进完成 → 占位节点更新为真实节点、生成记录置成功 → Realtime 推达，画布与对话同步更新为完成态。

**画布上的元素编辑**：用户拖动 / 缩放 / 增删节点 → 本地状态即时反映 → 交互结束后经 PostgREST 把节点的最终位置 / 尺寸 / 层级 / 内容写回画布节点表 → 数据库触发器更新项目时间戳与（必要时）缩略图 → Realtime 把变更广播到该用户的其他在线会话。

**项目归档与续作**：用户离开设计页 → 客户端确保最后的画布状态已持久化、并触发项目缩略图更新 → 用户回到主页，服务端组件查询其项目列表（按更新时间倒序）渲染「最近项目」→ 点击卡片 → 进入设计页，加载该项目的画布与会话，接续创作。

## 七、安全架构

安全设计围绕「最小信任、密钥不出边缘、数据按主隔离」三条原则。

**鉴权与会话**：用户经 Auth 登录获得 JWT；客户端访问 PostgREST 与 Storage 时携带该令牌，数据库据此建立 RLS 上下文；Edge Function 校验请求头中的令牌确认调用者身份后才执行。未登录用户无法访问任何业务数据。

**行级安全（RLS）**：所有业务表默认开启 RLS，策略以「资源归属于当前用户」为核心——用户只能读写归属自己的项目、画布节点 / 边、会话、消息、生成任务与资产。客户端的直连读写因此天然被约束在自己的数据范围内，无需中间业务层做权限校验。

**密钥隔离**：外部模型的 API 密钥、服务角色密钥等机密只存在于 Edge Function 的环境变量 / Vault 中，绝不下发到客户端，也绝不出现在数据库可被客户端读取的位置。任何需要密钥的调用都必须经由 Edge Function 代理。

**存储访问控制**：私有媒体对象不可被匿名直接访问，客户端通过签名 URL 在限定时间内访问；分享场景下生成可控、可撤销的访问凭据。Storage 的访问策略与数据库 RLS 一致，按用户隔离。

**滥用防护**：接口层施加速率限制与幂等键，防止重复提交与刷量；生成入口对接内容安全审核，拦截违规提示词与产出。

## 八、部署架构

前端 Next.js 应用支持两种等价的生产承载方式：其一部署在边缘渲染平台（如 Vercel），静态资源经 CDN 分发，服务端组件与服务端动作在平台的边缘 / 服务端运行时执行；其二以仓库提供的多阶段 Dockerfile 构建 standalone 生产镜像，通过 Docker Compose 一键运行在自有电脑或服务器。两种方式只改变 Next.js 的承载位置，不改变后端边界。Supabase 仍以托管云形态提供数据库、Auth、Storage、Realtime 与 Edge Functions；考虑到主要用户与开发者位于新加坡一带，数据库与边缘函数优先选择就近区域以降低延迟。Edge Functions 经 Supabase CLI 打包部署，密钥经平台机密管理注入；pg*cron 定时任务与 Database Webhooks 在数据库侧配置。环境区分开发、预发、生产三套，各自独立的 Supabase 项目与前端部署，配置经环境变量隔离，密钥不进版本库。Docker 部署只向镜像构建传入 `NEXT_PUBLIC*\*` 公开变量，服务角色和模型密钥仍只存在于 Supabase Edge Functions / Vault。可观测性上，前端容器通过 Compose 健康检查与日志观测；Edge Function 调用日志与指标、数据库性能、Realtime 连接、Storage 用量统一在 Supabase 控制台观测，并可外接日志汇出（Log Drains）到第三方监控。

## 九、可扩展性与性能

系统的可扩展性来自其无状态边缘与托管底座：Edge Functions 按请求自动伸缩，无需关心服务器容量；数据库可经连接池（Supavisor）承接高并发短连接，并可在读密集场景引入只读副本。性能上，画布以「仅渲染可视区域 + 节点记忆化 + 防抖持久化」控制前端开销，以「按项目分频道订阅」控制实时开销，以「分页加载项目与资产」控制列表开销；媒体经 Storage 的图片变换与 CDN 缓存降低传输与渲染成本。新增模型只需新增适配器与目录行，新增场景只需新增提示词模板与画布初始结构，二者都不触动核心架构，体现了「以配置驱动扩展」的设计取向。
