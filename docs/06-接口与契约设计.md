# 接口与契约设计

## 一、接口风格与分层

本系统不自建统一的应用网关，而是沿用第 02 篇确立的四层架构，把对外契约切分为三个正交的「契约面」，分别对应客户端与后端通信的三条通道。三者职责不重叠，共享同一套鉴权基线（Auth 签发的 JWT 与数据库行级安全）。

其一是**数据面**，由 Supabase 的 PostgREST 自动接口承载。常规业务数据的增删改查由客户端在行级安全（RLS）约束下经此通道直连数据库，无需为每张表手写后端接口。数据面是「读多写频、权限即数据」的场景的默认通道，承担项目列表、画布节点与边、会话与消息、资产与模型目录等的常规读写。

其二是**能力面**，由 Supabase Edge Functions 承载。一切需要持有密钥、需要服务端可信上下文、或需要多步编排的操作走此通道，包括调用外部模型、生成任务的落库与状态推进、智能体编排等。能力面是「不可下放到客户端」的逻辑的唯一受信入口。

其三是**实时面**，由 Supabase Realtime 承载。它是「结果上行」的通道：客户端按项目订阅频道，数据库中相关行的变更（生成结果落库、跨设备编辑）经此以毫秒级推回客户端。实时面只读不写——客户端从不向实时面写入，写入恒走数据面或能力面，变更再由实时面回流。

三个契约面的协作遵循一条主线：客户端经数据面做常规读写、经能力面发起敏感与生成操作，所有持久变更最终落入数据库这一真相之源，再由实时面把变化推回所有相关客户端，构成「意图下行、结果上行」的闭环。本篇逐一约定三个面的契约，并给出数据库行与画布节点的映射、统一错误约定与共享类型契约。

## 二、鉴权与调用上下文

全系统共用一套基于 JWT 的鉴权，由 Auth 签发，贯穿三个契约面。

客户端持有两类密钥语义。**匿名公钥（anon key）**用于初始化 Supabase 客户端，是可公开的项目标识，本身不授予任何数据权限；真正的权限来自登录后获得的用户 JWT。客户端在调用数据面、访问 Storage、订阅实时面时一律携带该用户 JWT，数据库据令牌中的用户标识建立 RLS 上下文，从而「令牌即身份、策略即权限」，无需中间业务层做鉴权。

**服务角色密钥（service role key）**拥有绕过 RLS 的最高权限，只存在于 Edge Function 的环境变量与 Supabase Vault 中，绝不下发到客户端、绝不出现在任何客户端可读的位置。能力面的函数在校验完调用者身份后，于必要的可信写入（生成落库、跨用户读取模型机密）时以服务角色执行。

能力面的每个面向客户端的 Edge Function 都遵循统一的鉴权前置：从请求头的 `Authorization` 中取出用户 JWT、校验其有效性、解析出调用者用户标识，再校验目标资源（如项目）归属于该用户，校验失败即以鉴权类错误拒绝，绝不进入业务逻辑。由队列、pg_cron 或提供商回调触发的内部型函数不持用户 JWT，改以队列消息中携带的归属信息、或回调签名校验来确认上下文，并同样以服务角色在受约束的范围内写入。外部模型的 API 密钥仅在能力面内部使用，对客户端与数据库均不可见。

## 三、PostgREST 数据访问契约

数据面是客户端读写常规数据的默认通道，其安全性完全由 RLS 兜底（策略详见第 03 篇第五节），契约层只约定「哪些资源可经此通道、以何种方式读写」。

下表列出数据面的资源清单与客户端权限。权限是 RLS 策略在接口契约上的投影，凡标注「只读」者，其写入只能经能力面以服务角色完成；凡标注「服务端写」者，客户端经数据面读取、但任何写入都不走数据面。

| 资源（表）    | 客户端权限                       | 典型操作                                                       | 关键约束                                           |
| ------------- | -------------------------------- | -------------------------------------------------------------- | -------------------------------------------------- |
| profiles      | 读写自身行                       | 读取档案、更新显示名 / 头像 / 语言偏好                         | 仅 id 等于当前用户的行                             |
| projects      | 读 / 增 / 改自身行，软删         | 列「最近项目」、建项目、改标题 / 视口 / 缩略图、置 is_deleted  | 仅 owner_id 等于自身；删除以软删表达               |
| canvas_nodes  | 读写所属项目的行                 | 加载画布、增 / 改 / 删节点、改位置 / 尺寸 / 旋转 / 层级 / 内容 | 经 project_id 关联校验项目归属；按节点粒度写入     |
| canvas_edges  | 读写所属项目的行                 | 加载与维护节点间血缘连线                                       | 同上                                               |
| conversations | 读写所属项目的行                 | 取 / 建会话、改标题                                            | 同上                                               |
| messages      | 读所属项目的行、写自身的用户消息 | 加载会话历史、乐观追加用户消息                                 | 用户消息可由客户端写入；助手消息由能力面服务端写入 |
| generations   | 只读所属项目的行                 | 展示历史生成、兜底查询任务状态                                 | 创建与状态 / 进度的写入恒由能力面服务端完成        |
| assets        | 读写自身行                       | 读取资产元信息、登记上传资产                                   | 仅 owner_id 等于自身；生成产出资产由服务端登记     |
| model_catalog | 只读（仅 is_active）             | 驱动模型选择条与参数 UI                                        | 上架 / 下架维护仅限管理侧                          |

读取约定如下。列表类查询（最近项目、资产、会话历史）一律分页，优先采用按时间游标（keyset，以 created_at / updated_at 配合主键）以在大数据量下保持稳定，小列表亦可用范围分页。过滤与排序直接表达为接口参数：「最近项目」按 owner_id 过滤、按 is_deleted 排除软删、按 updated_at 倒序，命中第 03 篇为此设计的复合索引；会话历史按 conversation_id 过滤、按 created_at 升序分页。画布的整体加载是一次按 project_id 取该项目全部 canvas_nodes 与 canvas_edges 的查询，节点按 z_index 取序以保证图层顺序；媒体不随节点查询返回，节点只携带 asset_id，真实媒体经 Storage 签名 URL 另行加载。需要关联读取时（如取项目同时带其会话）借助 PostgREST 的嵌套资源选择一次取回，减少往返。

写入约定如下。画布编辑以**节点为粒度**写回：拖动 / 缩放 / 旋转 / 改层级 / 改内容各自更新对应行的对应列，不整块覆盖画布，从而与「按节点最后写入胜出」的并发策略（第 02 篇第五节）一致。高频连续变更（拖动过程中的位移、缩放过程中的尺寸）不逐帧写库，而是先在画布状态库即时反映，待交互结束或防抖窗口到期再持久化（第 04 篇第三、五节）。新建元素在落点处先经屏幕到 flow 坐标换算得到逻辑坐标再插入节点行。用户消息作为对话乐观追加的一部分由客户端写入 messages，并把其标识传给能力面以触发生成。Storage 的上传经客户端取得签名上传凭据后直传，完成后在 assets 登记一行（来源为 upload）。

凡涉及密钥、外部模型调用、跨用户可信写入者，一律不在数据面进行，转由能力面承接。

## 四、Edge Function 能力契约

能力面以一组 Edge Function 暴露「不可下放」的能力。所有面向客户端的函数共享统一的调用与响应形态：经 HTTPS 以 POST 提交 JSON 请求体、在 `Authorization` 头携带用户 JWT、返回第五节约定的统一响应封套；内部型函数则由队列、pg_cron 或提供商回调触发，不面向客户端。下表给出函数清单与契约要点，随后逐一展开。

| 函数（逻辑名）                    | 触发者                    | 鉴权         | 主要副作用                                                         | 幂等                                     |
| --------------------------------- | ------------------------- | ------------ | ------------------------------------------------------------------ | ---------------------------------------- |
| 创建项目 create-project           | 客户端（主页发起创作）    | 用户 JWT     | 建 projects / conversations / 首条 messages，按需建首个 generation | 可选请求标识去重，重复不重建             |
| 提交生成 submit-generation        | 客户端（对话 / 画布工具） | 用户 JWT     | 建 generations（pending）、建占位节点、入队                        | 以 idempotency_key 去重                  |
| 消费队列 process-generation-queue | Supabase Queues           | 服务角色     | 取任务置 running、经适配器提交；同步模型直接落库完成               | 状态机单向转移，重复消费安全             |
| 轮询推进 poll-generations         | pg_cron 定时              | 服务角色     | 批量查运行中异步任务进度、回写状态；就绪则落库完成                 | 已终态任务跳过，重复轮询安全             |
| 回调推进 generation-webhook       | 外部提供商回调            | 回调签名校验 | 按外部任务号反查并推进、就绪则落库完成                             | 已终态忽略迟到回调                       |
| 智能体编排 agent-orchestrate      | 客户端（对话发送）        | 用户 JWT     | 理解意图、组织一到多次生成、写助手消息、流式回文                   | 同一消息重复发送可去重                   |
| 导出画布 export-canvas            | 客户端                    | 用户 JWT     | 按当前画布生成导出件、返回签名下载链接                             | 无状态，可重复调用                       |
| 重排海报 regenerate-poster        | 客户端（海报组工具）      | 用户 JWT     | 重新生成组背景、替换旧叠层并创建新可编辑文字节点                   | 生成任务按请求键去重，节点更新受事务约束 |
| 提供商凭证 provider-credentials   | 客户端（设置页）          | 用户 JWT     | 保存 / 启停 / 删除 BYOK Vault 凭证，执行连通测试                   | 每用户每提供商唯一，保存为 upsert        |
| 替换媒体候选 swap-media-candidate | 客户端（媒体候选卡）      | 用户 JWT     | 原子交换主媒体与候选媒体，保持主节点标识和引用关系                 | 同一事务完成交换，约束失败不产生半更新   |

**创建项目（create-project）**。用途是把主页的「发起创作」落地为一个可进入的设计页。它可实现为 Next.js 服务端动作（Server Action）或一个 Edge Function，二者契约一致。输入为初始想法（提示词文本）、所选模型键、所选场景（design / branding / ecommerce / video 之一或空）、可选附件资产引用。它在一个一致的边界内创建项目行（标题默认 Untitled，记录 initial_scene 与 default_model_key 与初始视口）、为该项目创建一条会话、写入首条用户消息；若产品策略为「进入即生成首图」，则同时按所选模型创建一条 pending 生成任务并入队（等价于一次 submit-generation）。输出为新项目标识，供客户端重定向至设计页（路径形如 p/{projectId}）。鉴权为校验调用者已登录。幂等上可接受一个可选的客户端请求标识，避免连点造成重复建项目。

**提交生成（submit-generation）**。用途是发起一次生成并立即给出可见反馈，是生成流水线的入口（流程详见第 05 篇第五节提交阶段）。输入为项目标识、会话标识、触发消息标识（可空）、模态、模型键、提示词、归一化的生成参数（尺寸 / 比例、数量、质量、随机种子等，按模型能力）、参考素材引用（来自 `@` 提及的画布节点或上传附件）、以及一个幂等键。它依次：校验调用者身份与项目归属；按所选模型在 model_catalog 的能力画像校验参数合法性，对不支持的参数按策略降级或拒绝；在 generations 建一条 pending 任务（写入模态、模型键、提供商、提示词、参数、幂等键）；在 canvas_nodes 建一个 generation_placeholder 占位节点并与任务互相关联；把任务投入 Supabase Queues。输出为生成任务标识与占位节点标识，客户端据此立即显示对话进行态与画布占位，后续进度与结果经实时面回流。鉴权为登录且项目归属本人。幂等以 generations.idempotency_key 的唯一约束保证：同一幂等键重复提交返回既有任务而不重复建任务。

**消费队列（process-generation-queue）**。用途是真正向提供商发起生成，是流水线的执行阶段。它由 Supabase Queues 投递触发，从队列取出待处理任务，将其置为 running，经适配器注册表按 provider 与 model_key 选定适配器并提交。对同步型模型，提交即得产出，直接进入结果落库；对异步型模型，记录提供商返回的外部任务号、保持 running，等待轮询或回调推进。它以服务角色运行，不面向客户端。幂等性由「状态机单向转移」保证：仅 pending 任务可被消费置 running，重复投递不会重复提交。

**轮询推进（poll-generations）**。用途是为异步任务兜底推进进度，是推进阶段的两条途径之一。它由 pg_cron 定时触发，批量拉取处于 running 且为异步的任务，经适配器查询语义向提供商查询进度，回写 generations.progress 与状态；任务就绪则进入结果落库，长时间停滞无进度者判定超时、置 failed。以服务角色运行。幂等上对已处于终态（succeeded / failed / cancelled）的任务跳过，重复轮询安全。

**回调推进（generation-webhook）**。用途是接收支持回调的提供商的完成通知，是推进阶段的另一条途径，与轮询互为兜底。它由外部提供商调用，先做回调来源与签名校验（不依赖用户 JWT），再按回调携带的外部任务号反查对应 generations 任务并推进，就绪则进入结果落库。幂等上对已终态任务忽略迟到回调，避免重复落库。回调缺失或丢失时，轮询仍能推进；回调及时到达时，结果比轮询更快反映。

上述三个推进 / 执行函数在任务到达成功时共享同一段**结果落库**逻辑（第 05 篇第五节完成阶段）：经适配器归一化得到资产候选；把媒体取回并写入 Storage 的 generations 桶、生成缩略图；在 assets 建资产记录；把占位节点原地转化为对应的 image / video 节点（改写 type、填入 asset_id、替换 data），多产出时首张落占位、其余在占位附近新建节点；把任务置 succeeded、写 completed_at。这组写入处于一致事务边界内，落库后由实时面把节点与任务变更推回客户端。失败与超时则置 failed、记录原因、占位节点转为可重试失败态。

**智能体编排（agent-orchestrate）**。用途是把右侧对话面板的自然语言意图翻译为生成与画布操作（模式详见第 05 篇第七节）。输入为项目标识、会话标识、用户消息内容、所选 Agent 模式、所选模型键、`@` 提及的画布节点引用与附件引用。它按模式呈现不同深度：纯生成模式直接转为一次 submit-generation 语义；编排式模式先以语言模型理解意图、再组织一到多次适配器调用并决定结果在画布上的落位；场景流程模式加载场景预置模板与画布初始结构。它把助手回复以服务角色写入 messages，文本回复经**流式响应**实时返回（边生成边显示），图像 / 视频产出则走异步生成流水线、稍后经实时面落画布。输出为流式的助手文本与（异步落地的）画布变更，时序由对话状态库协调。鉴权为登录且项目归属本人。幂等上对同一用户消息的重复发送可去重，避免重复编排。

**导出画布（export-canvas）**。用途是把当前画布导出为可下载的图像或工程件，对应项目菜单中的导出动作（保持轻量，不扩张为独立的素材市场或复杂版式系统）。输入为项目标识与导出选项（范围、格式、倍率）。它读取画布节点、按选项渲染或打包产出，写入 Storage 后返回短时效签名下载链接。鉴权为项目归属本人。无持久状态，可重复调用。

**重排海报（regenerate-poster）**。用途是把同一 `groupId` 下的背景图与文字 / 形状 / 手绘叠层作为一个海报组重新生成。函数校验项目归属和图像模型，读取现有文字形成 brief，经编排 LLM 产生新版式；背景以原图为参考原地生成，旧叠层被替换为新的可编辑节点，组标识保持不变。生成入队沿用统一限流与幂等逻辑，节点替换在受约束的写入边界内完成。

**提供商凭证（provider-credentials）**。用途是管理用户 BYOK，支持 `save`、`toggle`、`delete`、`test` 四种动作。函数验证用户 JWT，明文 API Key 只在边缘进程内出现，并经 `SECURITY DEFINER` RPC 写入 Vault；客户端只得到 provider、端点、末四位和启停状态等脱敏信息。每个用户对每个 provider 至多一条凭证，保存采用 upsert，删除同时清理 Vault secret。

**替换媒体候选（swap-media-candidate）**。用途是把某个候选图片 / 视频提升为主媒体，同时把旧主媒体放回候选位。函数校验项目归属后调用数据库事务函数完成交换，主节点 ID 保持不变，因此对话提及、媒体侧卡和其他引用关系不会丢失；任何约束失败都会整体回滚。

## 五、统一响应与错误约定

能力面的所有函数返回统一的响应封套，使客户端以一致方式处理成败。成功响应携带一个布尔成功标志与一个数据对象（其结构随函数而定，如生成任务标识与占位节点标识）。错误响应携带成功标志为否、一个稳定的机器可读错误码、一段可向用户展示且可本地化的消息、以及可选的细节对象（如校验失败的字段、提供商错误的原始摘要）。错误码保持稳定且与展示文案解耦：码用于客户端分支处置与埋点，文案随用户语言偏好本地化。数据面（PostgREST）的错误沿用其标准 HTTP 状态与错误体，客户端在数据访问层将其归一为同一套错误码语义后向上抛出，使上层无须区分错误来自哪个契约面。

下表给出错误码族与处置约定。

| 错误码             | 含义                   | 典型触发                        | 客户端处置                   |
| ------------------ | ---------------------- | ------------------------------- | ---------------------------- |
| unauthorized       | 未认证或令牌失效       | 缺失 / 过期 JWT                 | 引导重新登录                 |
| forbidden          | 已认证但无权访问该资源 | 访问他人项目                    | 提示无权限、返回安全位置     |
| invalid_params     | 请求参数不合法         | 缺字段、取值越界                | 校验提示，阻止提交           |
| unsupported_param  | 参数为目标模型不支持   | 向不支持比例 / 参考图的模型传入 | 按能力画像降级或提示更换模型 |
| not_found          | 资源不存在             | 项目 / 任务标识无效             | 提示并刷新列表               |
| content_blocked    | 内容安全拦截           | 违规提示词 / 产出               | 说明拦截原因、允许修改重试   |
| model_unavailable  | 模型不可用             | 模型下架 / 维护                 | 提示更换模型                 |
| provider_error     | 上游提供商错误         | 外部接口报错                    | 提示稍后重试                 |
| generation_timeout | 生成超时               | 任务长时间停滞                  | 提示超时，可重试             |
| duplicate_request  | 重复请求（幂等命中）   | 同一幂等键重复提交              | 复用既有任务结果，不报错呈现 |
| conflict           | 并发写入冲突           | 同一资源竞态写入                | 以较新版本为准，必要时重试   |
| rate_limited       | 触发速率限制           | 短时高频调用                    | 退避后重试，提示稍候         |
| internal_error     | 服务端内部错误         | 未预期异常                      | 通用错误提示，记录上报       |

## 六、Realtime 频道契约

实时面以「项目」为粒度组织。客户端进入设计页时订阅以项目标识命名的频道（命名形如 `project:{projectId}`），离开时取消订阅。订阅前提是携带有效用户 JWT，且频道授权确保客户端只能订阅自己有权访问的项目频道——授权与数据库 RLS 对齐，无权者订阅被拒。

频道监听数据库行变更（postgres_changes），覆盖三张已纳入 Realtime 发布的表，并以 project_id 等于当前项目为过滤条件，只接收本项目的事件。下表给出监听契约。

| 表           | 监听事件                  | 客户端响应                                         |
| ------------ | ------------------------- | -------------------------------------------------- |
| canvas_nodes | 插入 / 更新 / 删除        | 在画布状态库中按节点增 / 改 / 删，驱动对应节点渲染 |
| canvas_edges | 插入 / 更新 / 删除        | 维护节点间血缘连线                                 |
| generations  | 更新（状态 / 进度）/ 插入 | 更新占位节点的进度与完成态、对话进行态             |

事件载荷依赖第 03 篇为这三张表设置的完整副本标识（replica identity full），因而变更事件携带足够的旧值与新值，客户端据事件类型与新 / 旧值做精确的局部更新，而非整表重拉。生成结果的落地正是经此实现：占位节点被原地转化为真实节点这一行更新，作为 canvas_nodes 的更新事件推达，客户端据此把占位卡片替换为成品。

**回声抑制**是实时面与数据面协同的关键约定。由本端发起的写入（拖动后持久化、提交生成创建占位）会经实时面回流到自身，客户端须识别并抑制这类回声，避免对自己刚做的本地变更做无谓重置或闪烁。识别依据为节点携带的更新时间与本地版本比较（远端不更新于本地者忽略），以及对本端在途写入的标记。并发写入整体遵循「按节点最后写入胜出」（第 02 篇第五节）：远端回流的节点变更若更新于本地版本则覆盖本地。

messages 表可按需纳入发布，以支持同一用户多设备 / 多标签页下对话流的实时追加。其余表（profiles 等）不纳入实时发布。Realtime 的广播（broadcast）与在线状态（presence）能力为未来的多人协作预留，不在当前范围。

## 七、数据库行与画布节点映射

这是数据面与画布引擎之间的核心契约：`canvas_nodes` 表的一行与一个 React Flow 节点（`Node<T>`）双向对应，`canvas_edges` 的一行与一条 React Flow 边（`Edge`）对应。映射集中实现于第 04 篇所述数据层的映射模块，是行数据与画布对象之间唯一的转换处，避免坐标系与字段错配散落各处。

节点映射如下表。通用的几何与层级信息已在第 03 篇提为独立列，类型私有内容收在 data。

| 数据库列（canvas_nodes） | React Flow 节点字段               | 说明                                                   |
| ------------------------ | --------------------------------- | ------------------------------------------------------ |
| id                       | id                                | 同一标识，行 id 即节点 id                              |
| type                     | type                              | 与 nodeTypes 注册键、node_type 枚举三者一一对应        |
| position_x / position_y  | position.x / position.y           | flow 逻辑坐标，与视口解耦                              |
| width / height           | 节点尺寸（width / height 或样式） | 缩放手柄写回此二列                                     |
| rotation                 | data 内旋转角                     | 由节点内容容器以 CSS 变换应用（React Flow 无原生旋转） |
| z_index                  | 节点层级                          | 越大越靠前，加载时按其取序                             |
| parent_id                | 父节点关系（parentId / extent）   | 归属于某画板 frame 时建立父子，约束子节点范围          |
| data                     | data                              | 随 type 变化的判别联合内容                             |
| asset_id                 | data 内资产引用                   | 图片 / 视频节点据此经签名 URL 加载媒体                 |
| generation_id            | data 内生成引用                   | 占位节点据此订阅关联任务进度                           |

反向映射对称：前端节点的变更写回行的对应列——位移写 position_x / position_y、缩放写 width / height、旋转写 rotation、改层级写 z_index、改内容写 data。这一对称保证「画布上所见」与「数据库所存」始终可互相还原。

节点的 data 是一个随 type 变化的判别联合，其逐类型结构在第 03 篇第七节与第 04 篇第 4.4 节已完整定义，此处不重复展开，仅给出映射要点：image 节点的 data 提供裁剪 / 滤镜 / 圆角 / 透明度等展示属性并经 asset_id 取媒体；text 节点的 data 提供文本串与字体 / 字号 / 字重 / 行高 / 对齐 / 颜色等排版属性，直接驱动可编辑文本框；shape 节点的 data 提供形状种类与填充 / 描边 / 圆角，驱动内联 SVG；drawing 节点的 data 提供矢量路径与笔触参数，驱动 SVG 路径；video 节点的 data 提供封面 / 播放控制 / 区间并经 asset_id 取媒体；generation_placeholder 节点的 data 提供提示词摘要与目标尺寸并经 generation_id 订阅进度，任务成功后该行被原地改写为 image / video 节点（type 改写、asset_id 填入、data 替换），这一改写经实时面以 canvas_nodes 更新事件推达；frame 节点的 data 提供画板名 / 尺寸预设 / 背景，作为其他节点的父容器。

边映射如下表，边主要用于记录可选的生成血缘，非画布主要构件。

| 数据库列（canvas_edges）      | React Flow 边字段           | 说明                            |
| ----------------------------- | --------------------------- | ------------------------------- |
| id                            | id                          | 行 id 即边 id                   |
| source_node_id                | source                      | 源节点                          |
| target_node_id                | target                      | 目标节点                        |
| source_handle / target_handle | sourceHandle / targetHandle | 连接点（可空）                  |
| type                          | type                        | 边类型，如 lineage 表示生成血缘 |
| data                          | data                        | 边附加数据                      |

## 八、共享类型契约

前端与能力面（Edge Functions）共享一组类型定义，作为跨层的静态契约，集中维护于第 04 篇工程结构中的类型目录（types/），由客户端与函数共同引用，确保两端对同一数据结构的理解一致、字面量取值不漂移。这些类型与数据库的枚举及 JSONB 结构严格对齐：枚举类型（modality、generation_status、message_role、asset_kind、asset_source、node_type）在类型层以同名字面量联合表达，取值与第 03 篇逐字一致。

共享契约涵盖以下结构。**节点数据判别联合**以 type 为判别标签，为每种节点类型（image / text / shape / drawing / video / generation_placeholder / frame）定义其 data 形状，是数据面映射与画布渲染共同依赖的契约。**边数据**定义 canvas_edges.data 与边类型取值。**统一生成请求**定义 submit-generation 与 agent-orchestrate 接受的请求形状，含模态、模型键、提示词、按模态划分的参数子集（图像、视频、文本三套，与第 05 篇第四节一致）、参考素材引用与幂等键。**资产候选**定义适配器归一化（normalize）的输出形状——媒体的获取方式、模态、尺寸 / 时长等元信息，是流水线落库的输入契约（与第 05 篇适配器抽象一致）。**消息结构**定义 messages 的 mentions 与 attachments 两个 JSONB 数组的形状：mentions 为被 `@` 提及的画布节点引用列表（节点标识与类型），attachments 为附件资产引用列表（资产标识与元信息），与第 03 篇 messages 表一致。**模型能力画像**定义 model_catalog.capabilities 的形状（支持的比例与尺寸、单次最大产出数、是否支持参考图 / 图生图 / 图生视频、是否异步），既驱动前端参数 UI、又供流水线校验。**响应封套与错误码**定义第五节的成功 / 错误封套与错误码字面量联合。

`@` 提及把画布上的具体元素带入生成上下文，因而 mentions 的节点引用结构与节点映射、与生成请求的参考素材引用三者必须共用同一套标识语义——提及的节点标识即 canvas_nodes 行标识，经引用在生成时被解析为参考图 / 首帧传入对应适配器。共享类型是这一串联得以类型安全的基础。

## 九、幂等、限流与并发

**幂等**贯穿生成链路。提交端以 generations.idempotency_key 的唯一约束去重，同一幂等键重复提交返回既有任务而不重复建任务（对应错误约定中的 duplicate_request，以复用结果而非报错的方式呈现）。推进与完成端以「状态机单向转移」防止重复落库：任务状态只能沿 pending → running →（succeeded / failed / cancelled）单向前进，已处于终态者忽略一切迟到的轮询结果与回调通知。结果落库的多处写入（Storage、assets、canvas_nodes、generations）处于一致事务边界，保证「要么全成、要么全不成」。

**限流**在能力面施加，仅作防滥用兜底、与计费无关。接口层按用户施加速率限制，短时高频调用以 rate_limited 拒绝并提示退避重试；并可对单用户在途生成数设一个上限以防刷量。系统不设凭证、配额或套餐，生成不计量、不计费。

**并发**以两条机制保证安全。画布的并发写入按节点粒度最后写入胜出，依据节点更新时间裁决（第 02 篇第五节），主要应对同一用户多设备场景。Supabase Queues 保证任务至少一次投递，消费端以状态机幂等处理重复投递。

**重试**分两类。执行阶段对可重试的瞬时错误（网络抖动、提供商限流）做有限次自动重试与退避，超过上限才置失败。用户侧对失败任务一键重试，以原参数新建一条任务而非复用已失败记录，以保审计清晰（第 05 篇第五、六节）。

## 十、契约稳定性与演进

对外契约以向后兼容为准则演进。统一响应封套与错误码保持稳定，新增错误码不影响既有分支，新增响应字段一律可选、不破坏既有解析。模型与场景的扩展经数据驱动完成——新增模型只需实现适配器、注册并在 model_catalog 追加一行，新增场景只需追加提示词模板与画布初始结构，二者都不改动 submit-generation、agent-orchestrate 等函数的接口形状，自动被前端选择条、参数 UI 与流水线纳入（第 05 篇第十一节）。共享类型随结构演进时，以新增可选字段优先、避免破坏性变更。

实时面的广播与在线状态、分享场景的可撤销访问凭据、导出能力的增强，均为预留的演进方向，标注为非当前范围，以与第 01 篇确立的范围边界（仅实现两张界面草图所示功能，不含多人实时协作、评论、素材市场等）保持一致。本套接口契约据此在「当前精确实现」与「未来低成本扩展」之间取得平衡。
