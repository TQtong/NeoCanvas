# 现状审计与问题清单

## 目标

本文固化优化开始前的工程基线、已验证能力、问题证据和优先级，作为后续整改与回归测试的共同输入。审计结论来自当前仓库源码、现有脚本和本地生产构建，不把尚未验证的预期能力写成完成状态。

## 现状问题

### 工程基线

审计时仓库约包含 190 个 TypeScript、TSX 与 SQL 文件，合计约 26,000 行。主要检查结果如下：

| 检查项                 | 结果                       | 结论                                                                                            |
| ---------------------- | -------------------------- | ----------------------------------------------------------------------------------------------- |
| `npm run typecheck`    | 通过                       | 根前端 TypeScript 严格检查可通过，但 `tsconfig.json` 排除了 `supabase/functions`                |
| `npm run lint`         | 通过并产生 1 条警告        | 使用已经弃用的 `next lint`；`components/shared/Avatar.tsx` 使用原生 `<img>`                     |
| `npm run build`        | 通过并产生运行时与缓存警告 | 设计页首屏 JavaScript 约 335 kB；Supabase SSR 在 middleware 的 Edge Runtime import trace 需消除 |
| `npm run format:check` | 失败                       | 52 个文件存在格式漂移，当前仓库不具备可执行的格式门禁基线                                       |
| 自动化测试             | 缺失                       | 未发现 Vitest、Playwright 或 Deno 测试配置与测试文件                                            |
| Deno 静态检查          | 未执行                     | 本机未安装 Deno，现有 npm 脚本也未覆盖 Edge Function                                            |

本地浏览器验证确认主页可以在已登录状态渲染创作输入框、模型选择、最近项目和设置入口；该结果仅证明主页首屏可用，不代表设计页核心链路已经完整。

### 已具备的可靠基础

- Next.js App Router、React 19、严格 TypeScript、Zustand 与 React Flow 的分层结构清晰。
- 数据库表、RLS、Storage、Realtime publication、队列、定时任务、Edge Function 和多模型适配器已经形成主体。
- Provider 凭据写入 Vault，API 密钥不返回客户端；service-role 未出现在前端公开环境变量中。
- 项目列表具备分页，媒体使用私有 Storage 与签名 URL，画布以一节点一行的方式持久化。
- Docker 与 Supabase 重建路径已经文档化，具备从空项目重建结构的方向。

### 问题台账

| 编号 | 优先级 | 问题与证据                                                                                                 | 主要影响                                                      |
| ---- | ------ | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| C-01 | P0     | `DesignWorkbench` 只水合 CanvasStore，未水合 ChatStore；`ChatPanel` 没有被任何页面挂载                     | 设计真相定义的右侧对话主链路在实际页面不可用                  |
| C-02 | P0     | `useRealtimeProject` 只接收 `projectId`，没有订阅当前 `conversationId` 的消息；生成更新只进入 CanvasStore  | 跨页面消息与生成状态无法完整回流到对话界面                    |
| C-03 | P0     | 保存 debounce 触发的异步 flush 可以重叠；失败处理只恢复删除集合，未恢复失败 upsert                         | 后写覆盖、顺序反转或静默丢失编辑                              |
| C-04 | P0     | `createGeneration` 依次写任务、占位、候选节点与队列，不在同一事务                                          | 中间失败会遗留不完整 pending 任务或孤立节点，幂等重试无法自愈 |
| C-05 | P0     | 结果落库前的终态判断在 RPC 外，RPC 内没有行锁终态门禁                                                      | webhook 与轮询并发时可能重复创建资产、节点或关系              |
| C-06 | P0     | `process-generation-queue` 与 `poll-generations` 关闭网关 JWT 校验，函数内缺少严格 service-role 调用者验证 | 外部调用者可能触发内部批处理，扩大资源消耗与攻击面            |
| C-07 | P0     | 根 `types/` 与 `supabase/functions/_shared/types.ts` 双份维护；Edge 代码未进入现有类型与 Lint 检查         | 契约和枚举可静默漂移，错误推迟到部署后暴露                    |
| R-01 | P1     | Realtime 断线重连后不拉取权威快照，订阅状态未用于界面或恢复流程                                            | 断线窗口内的变更可能永久缺失                                  |
| R-02 | P1     | 当前撤销签名只覆盖位置、尺寸和层级，忽略文本、样式、旋转与边；拖拽历史按防抖末帧记录                       | 撤销不完整，且一次拖拽可能只回退很小距离                      |
| R-03 | P1     | 媒体签名 URL 有效期约一小时，`useCanvasMedia` 主要只补充缺失 `src`                                         | 长时间打开的工作台会出现图片或视频失效                        |
| R-04 | P1     | 每个 `MediaPanelNode` 都请求模型目录和 Provider 凭据                                                       | 画布节点增多时形成 N+1 数据库请求与重复订阅                   |
| R-05 | P1     | 多选变换逐节点调用 `updateNode`，每次都扫描节点数组；历史与媒体钩子也在节点变更时全量扫描                  | 框选拖动和千节点交互出现 O(k×n) 或持续 O(n) 热点              |
| R-06 | P1     | `create-project` 的模型查询使用管理员客户端，未明确限制内置模型或当前用户所有模型；幂等查询未绑定所有权    | 可能引用其他用户模型，或让错误幂等键命中非当前作用域数据      |
| P-01 | P2     | 顶栏分享仅复制当前私有 URL，版本入口禁用，导出 Edge Function 无客户端入口                                  | 产品完整度不足，但不阻断核心闭环稳定化                        |
| P-02 | P2     | AI 文本工具当前只创建普通文本节点                                                                          | 命名与实际行为不一致，应在核心链路稳定后单独设计              |

## 实施方案

问题按依赖关系分组整改：

1. C-01、C-02 与 R-01 由[《对话与实时同步优化》](./02-对话与实时同步优化.md)解决，先恢复完整工作台，再建立重连快照校正。
2. C-03、R-02 至 R-05 由[《画布可靠性与性能优化》](./03-画布可靠性与性能优化.md)解决，保存正确性先于批处理与性能优化。
3. C-04 至 C-06、R-06 由[《生成事务与安全优化》](./04-生成事务与安全优化.md)解决，事务、幂等和鉴权必须在数据库及 Edge 边界共同收紧。
4. C-07 与工程基线缺口由[《类型契约与工程质量》](./05-类型契约与工程质量.md)解决。
5. 全部问题的自动化证明由[《测试计划与上线验收》](./06-测试计划与上线验收.md)统一编排。

P2 能力不在本轮实施范围内；再次启动时必须先核对现有 `docs/00–06` 的范围约束，并以独立需求、接口和验收标准落地。

## 接口变化

审计本身不修改运行时接口。后续改造预计新增以下兼容性契约：

- 客户端 `RealtimeStatus`、`SyncState`、`OutboxEntry`、历史操作差异和 `AssetView.expiresAt`。
- `useRealtimeProject(projectId, conversationId)`、`updateNodesBatch(changes)` 和工作台级模型/凭据数据源。
- 数据库 `create_generation_submission` 与 `land_generation_result_once` RPC。
- 由根 `types/` 生成的 Edge 契约文件与漂移检查命令。

每项准确字段、调用顺序与兼容策略以对应专题为准。

## 失败处理

审计项若在实施前已经被其他变更修复，不直接删除记录，而是保留编号并补充修复提交、验证命令和验证日期。若验证结果与本审计不同，先排除环境差异、未提交改动和依赖版本差异，再更新基线。

任何 P0 问题复现失败都不能被解释为风险消失；只有存在针对其失败路径的确定性自动化测试，并在 CI 连续通过，才能关闭问题。P1 性能问题必须同时记录节点数量、交互动作、浏览器与测量方式，避免用不可比较的数据宣布改善。

## 测试与验收

本文的验收条件是审计可重复：

- 所列命令在固定 Node 与依赖版本下能够复现相同类别的结果。
- 每个 P0/P1 编号都能映射到一个实施章节和至少一个自动化测试。
- 修复完成后，台账增加“已验证”证据，而不是仅根据代码存在进行关闭。
- P2 项未混入本轮核心稳定变更，业务代码与数据库变更均由相应专题和设计真相授权。
