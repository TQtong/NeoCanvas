# 生成事务与安全优化

## 目标

使一次生成任务从提交、排队、轮询或 webhook 回调到结果落库具备明确的事务边界、所有权校验和并发幂等性。无论外部提供商重复回调、队列重投、轮询与 webhook 并发，数据库都只提交一份业务结果；内部批处理只能由可信服务调用。

## 现状问题

- `_shared/create-generation.ts` 依次创建 generation、占位节点、候选关系/面板、回写 linkage 并入队，多个写入不在同一数据库事务。
- 任一中间步骤失败都可能留下无法继续的 pending generation、缺少 linkage 的占位或孤立边；同一幂等键再次请求可能只返回这条不完整记录。
- pipeline 在调用 `land_generation_result` 前读取一次任务终态，但读取与提交不在同一锁内。轮询和 webhook 都看到未完成时，可以同时上传对象并调用 RPC。
- 现有结果 RPC 没有在事务内锁定 generation 并判断终态；候选边与媒体面板还有部分写入发生在 RPC 之后。
- Storage 上传发生在数据库提交之前，RPC 失败时缺少对应对象补偿，可能形成孤立文件。
- `create-project` 使用管理员客户端查询模型，未把模型访问限制明确绑定到“内置可用或当前用户所有”；生成幂等查询也需要绑定用户和项目作用域。
- `process-generation-queue` 与 `poll-generations` 配置为 `verify_jwt = false`，函数内部没有验证调用者持有 service-role。`generation-webhook` 同样关闭网关 JWT，但它应使用提供商签名而不是 service-role。

本节保留优化前的风险基线；当前实现状态见“实施状态与证据”。

## 实施方案

### 1. 原子提交生成 RPC

新增 `public.create_generation_submission`，在一个 PostgreSQL 事务中完成：

1. 依据 `auth.uid()` 或显式传入且已验证的用户 id 锁定项目，并验证项目所有权。
2. 验证 model catalog 条目处于启用状态，且模型是内置模型或属于当前用户；自定义 Provider 凭据必须存在且可用。
3. 在 `(user_id, project_id, idempotency_key)` 唯一约束下查询或创建 generation。
4. 若幂等命中，验证现有记录关联的请求摘要、会话和项目完全一致；一致则返回完整现有 submission，不一致返回 `IDEMPOTENCY_CONFLICT`。
5. 创建或 upsert 生成占位节点、媒体候选面板及血缘边，写回 generation 的 placeholder/linkage。
6. 将任务写入持久队列；队列写入失败则整个数据库事务回滚。
7. 返回 generation、节点、边和队列标识组成的完整结果。

Edge Function 仍负责身份验证、请求 Zod 校验和将外部输入规范化，但不再自行串联多次数据库写入。RPC 只授予 service-role 执行，普通 authenticated 角色不能绕过 Edge Function 直接提交管理员语义参数。

### 2. 生成结果只落库一次

以 `public.land_generation_result_once` 替代现有结果路径。RPC 在单一事务内：

1. `SELECT ... FOR UPDATE` 锁定 generation 行，并验证 generation、project、user 和 placeholder 关联一致。
2. 若状态已是 `succeeded`、`failed` 或 `cancelled`，返回 `{ landed: false, terminalStatus }`，不写任何资产、节点、边或消息。
3. 对仍可完成的任务写入 assets，更新首个占位节点，创建额外输出节点、候选面板和血缘边。
4. 更新 generation 为 `succeeded`，写入 provider 输出摘要、完成时间和关联资产；所有写入一起提交。
5. 返回 `{ landed: true, generationId, assetIds, nodeIds }`。

所有业务结果只在该 RPC 中落库。轮询、webhook 和队列处理器都调用同一 pipeline，不得在 RPC 前后另行创建候选边、面板或结果节点。

### 3. Storage 暂存与补偿

外部二进制结果先上传到任务专属暂存前缀，例如 `staging/{userId}/{generationId}/{attemptId}/`。上传完成后将对象元数据作为 RPC 参数；只有 `landed: true` 的尝试被登记为资产并转入正式引用。

若 RPC 返回 `landed: false`，当前尝试负责删除自己上传的暂存对象。RPC 或网络失败时保留短期暂存对象并记录 attempt id，由补偿任务根据“未被 assets 引用且超过安全窗口”清理。补偿清理只作用于明确的 staging 前缀，不能扫描删除业务正式对象。

### 4. webhook 与轮询并发控制

- 每次 provider submission 保存 provider task id，并对 `(provider, provider_task_id)` 建唯一约束。
- webhook 验证提供商签名、时间戳与重放窗口，再通过 provider task id 定位 generation。
- poller 获取待查询任务时使用 `FOR UPDATE SKIP LOCKED` 或队列租约，避免多个批次同时轮询同一任务。
- webhook 与 poller 即使同时得到结果，也由 `land_generation_result_once` 的行锁和终态判断决定唯一胜者。
- 失败状态同样通过事务内 `fail_generation_once` 或等价终态门禁提交，成功与失败不能相互覆盖。
- 重复事件记录为幂等命中指标，不作为错误反复触发重试。

### 5. 模型归属与幂等作用域

所有创建项目、提交生成和智能体编排入口共享同一模型访问函数：

- 内置模型必须为 enabled，并满足场景与 modality 要求。
- 用户自定义模型必须满足 `owner_id = current_user_id` 且其 Provider 凭据属于同一用户。
- 请求不得仅因知道 model id 而通过 service-role 读取并使用其他用户记录。
- idempotency key 必须与 user、project 和操作类型组成唯一作用域；相同 key 携带不同请求摘要时明确返回冲突。

### 6. 内部 Edge Function 鉴权

`process-generation-queue` 与 `poll-generations` 保留适合 pg_cron/队列调用的部署配置，但在函数入口强制验证 `Authorization: Bearer <SUPABASE_SERVICE_ROLE_KEY>`，使用恒定时间比较并拒绝缺失、格式错误或不匹配的请求。函数不接受普通用户 JWT，不通过 query 参数传递内部密钥。

`generation-webhook` 不使用 service-role 作为外部提供商凭据；它按适配器验证签名、时间戳和原始请求体，并将验证后的事件映射到内部 pipeline。无法提供签名能力的 Provider 使用不可猜测的每任务回调 secret，并限制重放窗口。

内部函数只从服务端环境读取密钥，日志禁止输出 Authorization、Provider 凭据、完整 webhook secret 和原始敏感 payload。

### 7. 数据库迁移与兼容策略

迁移采用扩展后切换：

1. 新增幂等唯一索引、provider task 唯一索引、attempt/staging 元数据和两个新 RPC，不删除旧函数。
2. 在空 Supabase 项目运行全部迁移和种子，验证函数权限、RLS、队列与 Realtime publication。
3. 部署兼容新旧数据行的 Edge Function，并将写路径切到新 RPC。
4. 观察一个完整生成周期，确认没有旧路径调用后再撤销旧 RPC 的 execute 权限。
5. 旧函数的删除放入后续独立迁移，确保前端或 Edge 回滚期间仍可读取历史记录。

迁移只改变结构与函数，不复制测试环境业务数据、Auth 用户、Storage 对象、Docker 卷或环境文件。

## 接口变化

数据库新增两个核心返回契约：

```ts
interface GenerationSubmissionResult {
  generationId: string;
  placeholderNodeId: string;
  nodeIds: string[];
  edgeIds: string[];
  queueMessageId: string;
  reused: boolean;
}

interface LandGenerationResult {
  landed: boolean;
  generationId: string;
  terminalStatus: 'succeeded' | 'failed' | 'cancelled';
  assetIds: string[];
  nodeIds: string[];
}
```

`submit-generation`、`create-project`、`agent-orchestrate` 和 `regenerate-poster` 的现有 HTTP 请求字段与响应封套保持兼容，内部统一转调 `create_generation_submission`。响应可新增 `reused` 等可选元数据，旧客户端忽略时不影响流程。

错误码至少区分 `MODEL_NOT_ACCESSIBLE`、`IDEMPOTENCY_CONFLICT`、`PROJECT_FORBIDDEN`、`GENERATION_TERMINAL`、`PROVIDER_SIGNATURE_INVALID` 和 `INTERNAL_AUTH_REQUIRED`，并纳入根共享类型源。

## 实施状态与证据（2026-08-25）

- 第 23–26 号迁移实现并规范化 `create_generation_submission`、单次 landing、暂存 attempt、清理领取、poll lease、幂等作用域、模型归属与函数权限；迁移均为前向兼容扩展。
- `submit-generation`、`create-project`、`agent-orchestrate`、海报重生成和媒体候选路径统一使用原子 submission；空白项目不再被硬编码模型阻断，只有需要生成时才强制可访问模型。
- pipeline 先写 Storage staging，再由数据库行锁提交唯一业务结果；未获胜 attempt 标记丢弃并进入幂等清理。webhook 使用 Provider HMAC 或任务级临时 secret、时间窗口与事件键防重放，poller 使用数据库租约避免重复处理。
- 内部队列处理、轮询和清理只接受精确 service-role Bearer token，并限制为 POST；模型查询同时校验启用状态、modality、内置模型或当前用户归属和可用凭据。
- 测试专用确定性 Provider 只在 `NEOCANVAS_TEST_MODE=true` 且非生产环境时启用，可覆盖同步、异步、失败和超时，不携带真实计费凭据。

数据库证明位于 [`generation_transactions.test.sql`](../../supabase/tests/generation_transactions.test.sql)（31 个 pgTAP）与 [`generation-concurrency.test.ts`](../../supabase/tests/integration/generation-concurrency.test.ts)（20 轮并发 submission + 20 轮并发 landing）。鉴权、签名、请求摘要与测试 Provider 由 Deno 测试覆盖。全新影子库已完整应用第 1–26 号迁移且与本地 public schema 零差异。

## 失败处理

| 失败点                         | 处理                                                                |
| ------------------------------ | ------------------------------------------------------------------- |
| 创建事务任一步失败             | 整个 submission 回滚，不产生 pending generation、占位、边或队列残留 |
| 幂等命中完整任务               | 返回同一完整 submission，绝不重复入队                               |
| 幂等命中但请求摘要不同         | 返回 409 `IDEMPOTENCY_CONFLICT`，不复用也不创建新任务               |
| 外部提交成功但本地记录响应失败 | 通过 provider task id 和幂等键恢复，不盲目再次提交付费请求          |
| 结果上传后 RPC 失败            | attempt 保留在 staging，记录清理期限并重试同一幂等 landing          |
| webhook 与 poller 同时完成     | 首个事务落库，后一个得到 `landed: false` 并清理自己的 staging       |
| 内部鉴权失败                   | 返回 401/403，拒绝访问队列与管理员客户端，不记录敏感 header         |
| webhook 签名失败或过期         | 返回 401，记录 Provider、事件摘要和原因，不更新 generation          |

## 测试与验收

- Deno/数据库集成测试在每一个 submission 步骤注入失败，确认事务回滚后 generation、节点、边和队列均无残留。
- 相同 user/project/key 的并发请求只创建一个完整任务；不同用户或不同请求摘要不能复用该任务。
- 模型访问测试覆盖内置启用、内置停用、当前用户自定义、其他用户自定义、缺失凭据和 modality 不匹配。
- 以屏障同时释放 webhook 与 poller 的 landing 请求，重复执行多轮，最终只有一组 assets、节点、边和终态；失败尝试的 staging 被清理。
- 成功、失败与取消三类终态互不覆盖，迟到事件只增加幂等命中指标。
- 不带 token、普通用户 JWT、错误 service-role 均无法调用内部批处理；正确内部凭据可以调用且日志不包含密钥。
- webhook 的正确签名可处理，错误签名、过期时间戳和重复事件分别被拒绝或幂等忽略。
- 全新空 Supabase 项目可以从迁移、种子和函数部署重建全部结构，现有 HTTP 客户端契约测试保持通过。
