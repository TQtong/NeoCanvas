# 画布可靠性与性能优化

## 目标

把画布编辑从“防抖后尽量保存”升级为可观察、可恢复、顺序确定的持久化系统，并在不改变“一节点一行、数据库是真相来源”的前提下，治理撤销/重做、批量变换、媒体续签和千节点性能。

核心不变量是：任何已经向用户显示为本地成功的编辑，要么最终写入数据库，要么保持为明确可恢复的未同步记录；不能因请求重叠、刷新、短暂断网或签名 URL 到期而静默丢失。

## 现状问题

- `use-canvas-persistence` 的 debounce 回调可在上一次异步 flush 未结束时再次启动，无法保证同一实体的提交顺序。
- `flushDirty()` 取走脏集合后，`markPersistFailed()` 只恢复失败删除项，没有恢复节点和边的 upsert；一次 5xx 即可让本地更改退出待保存集合。
- pending、dirty 和失败状态没有统一映射成用户可见的“保存中、已保存、离线、失败”。刷新或关闭页面前也无法准确判断是否还有未落库操作。
- 当前撤销签名主要覆盖位置、尺寸与 zIndex，忽略内容、样式、旋转和边；全量快照最多保留 60 份，内存开销随节点数线性放大。
- 拖拽过程按防抖末帧捕获历史，撤销可能只回退最后一小段，而不是回到操作开始位置。
- 多选变换逐节点调用 `updateNode`，每次更新都扫描整个节点数组，形成 O(k×n) 热点。
- `useCanvasMedia` 在节点数组变化时扫描全部节点，且主要只解析缺失 `src` 的媒体；约一小时后签名 URL 到期，长会话资产会失效。
- 每个 `MediaPanelNode` 独立调用模型目录与 Provider 凭据钩子，节点数增长会带来 N+1 查询和重复订阅。

本节保留优化前基线；当前实现状态见“实施状态与证据”。

## 实施方案

### 1. 串行持久化队列

每个项目只允许一个正在执行的持久化批次。Store 中保留 `dirty`、`inFlight` 与 `queuedWhileSaving` 三类集合：

1. 用户操作写入 `dirty`，按实体键合并；同一实体的后写覆盖前写，删除优先于 upsert。
2. debounce 到期且没有 `inFlight` 时，把当前 `dirty` 原子移入一个不可变批次并清空 `dirty`。
3. 批次提交期间的新修改继续进入 `dirty`，不修改 `inFlight` 的 payload。
4. 当前批次成功后更新确认 revision；若 `dirty` 非空，立即开始下一批，不再额外等待 debounce。
5. 当前批次失败时按错误类别恢复或终止；下一批不得越过失败批次提交同一实体。

节点、边和 viewport 可以在同一调度器内分组调用现有持久化接口，但确认状态必须按实体键记录。客户端为每次本地修改生成单调递增的 `clientRevision`，旧响应不得确认比当前 revision 更新的本地状态。

### 2. IndexedDB outbox

使用名为 `neocanvas-outbox` 的 IndexedDB，`mutations` object store 以 `[projectId, entity, entityId]` 为复合键保存最后一个未确认操作：

```ts
interface OutboxEntry {
  projectId: string;
  entity: 'node' | 'edge' | 'viewport';
  entityId: string;
  operation: 'upsert' | 'delete';
  payload: unknown;
  clientRevision: number;
  createdAt: string;
  updatedAt: string;
}
```

本地操作先更新 Zustand 投影并写 outbox，随后才允许网络调度器发送。相同复合键执行合并：连续 upsert 只保留最新完整 payload，upsert 后 delete 只保留 delete，delete 后重新创建则保留带新 revision 的 upsert。

页面加载时先拉服务端快照，再读取该项目 outbox 并按 revision 重放到客户端投影；网络恢复后才提交。只有服务器确认对应 revision 后才能删除 outbox 条目。项目删除、退出登录或权限丢失时不得直接清空未确认 outbox，必须先提供明确提示，并允许用户导出恢复信息。

### 3. 保存状态与失败恢复

统一保存状态：

```ts
type SyncState =
  | { status: 'saved'; confirmedAt: string }
  | { status: 'saving'; pendingCount: number }
  | { status: 'offline'; pendingCount: number }
  | { status: 'error'; pendingCount: number; message: string; retryable: boolean };
```

网络错误、超时、429 和 5xx 视为暂时错误，按 1、2、4、8、16、30 秒上限指数退避，并在 `online`、页面重新可见或用户手动重试时立即唤醒。400、401、403、404、冲突校验失败视为永久错误，停止自动循环；先拉取权威实体，保留冲突副本并让用户选择恢复或放弃。

`beforeunload` 只用于提示存在未同步 outbox，不依赖在卸载期间完成异步请求。状态展示在顶栏，和 Realtime 连接状态分开表达：Realtime 已连接不代表本地写入已经保存。

### 4. 操作差异式撤销/重做

历史从全量画布快照改为操作事务：

```ts
interface CanvasHistoryEntry {
  id: string;
  label: string;
  nodesBefore: Record<string, CanvasNode | null>;
  nodesAfter: Record<string, CanvasNode | null>;
  edgesBefore: Record<string, CanvasEdge | null>;
  edgesAfter: Record<string, CanvasEdge | null>;
  createdAt: string;
}
```

指针按下或键盘操作开始时捕获受影响实体的 before，指针释放或命令完成时捕获 after；一次拖拽、缩放、旋转、对齐、删除或粘贴只生成一个历史条目。文本、样式、节点数据、位置、尺寸、旋转、层级和边均进入差异。内容完全相同的操作不入栈。

保留最多 60 个事务。执行 undo/redo 时通过与普通编辑相同的批量更新和 outbox 管道持久化，不能直接绕过保存系统。远端 Realtime 变更不加入本地撤销栈；若命中本地历史涉及的实体，以数据库 revision 和未提交 mutation 状态决定校正，不能回滚其他页面的已确认操作。

### 5. 批量节点更新

CanvasStore 增加 `updateNodesBatch`，一次遍历完成多节点变更并生成一个历史事务、一个脏批次和一次 React 状态更新。多选移动、缩放、旋转、对齐、分布和层级调整全部改用该接口。

内部以 `Map<nodeId, change>` 建立查找，复杂度从逐节点调用造成的 O(k×n) 降为 O(n+k)。批量接口必须复用现有几何约束、flow 坐标和节点判别联合，不能创建第二套节点变换规则。

### 6. 签名 URL 续签

媒体视图记录签名 URL 的确切到期时间：

```ts
interface AssetView {
  assetId: string;
  src: string;
  expiresAt: string;
}
```

签发端返回 `expiresAt`；若 Supabase API 只返回 URL，封装层使用签发时刻加服务端 TTL 计算。客户端在到期前 5 分钟续签，页面从休眠恢复、媒体加载返回 401/403 或 Realtime 通知资产变更时立即检查。相同 asset id 的并发续签采用 single-flight，并更新所有引用该资产的节点视图，不修改数据库中的 storage path。

媒体钩子只订阅资产引用集合的稳定签名，不因节点位置变化重新扫描或请求。无引用的 timer 立即释放。

### 7. 千节点性能治理

- 将模型目录与 Provider 凭据提升到工作台级单一数据源，通过精确 selector 或 Context 向媒体面板提供，只请求一次。
- 拆分 CanvasStore selector，节点组件只订阅自身数据与必要的选择状态，避免订阅完整 nodes 数组。
- 历史签名、媒体资产集合和候选关系改为增量索引，不在每次拖拽时执行全量序列化。
- 保留 React Flow 的可视区域渲染能力，稳定 nodeTypes/edgeTypes 和事件回调引用。
- 为 100、500、1,000 节点建立相同机器与浏览器下的基准，记录初次渲染、平移缩放、单节点拖拽、50 节点批量移动、内存占用和网络请求数。

性能优化不得通过降低历史正确性、停用 Realtime 或跳过持久化实现。

## 接口变化

CanvasStore 新增或调整以下接口：

```ts
type NodeBatchChange = {
  id: string;
  patch: Partial<CanvasNode>;
};

updateNodesBatch(changes: NodeBatchChange[], historyLabel: string): void;
flushNextBatch(): Promise<void>;
retryPending(): void;
getSyncState(): SyncState;
```

现有单节点 `updateNode` 可以作为对 `updateNodesBatch` 的单元素封装，保证调用方渐进迁移。媒体解析接口返回 `AssetView` 而不是裸字符串；过渡期允许读取旧缓存中的 `src`，但首次续签后统一写入带到期时间的结构。

数据库行结构不因 outbox 改变；如需端到端 revision，新增可空 `client_mutation_id` 或 revision 字段，并在旧客户端缺失时由服务端生成默认值。具体迁移须与现有[数据模型设计](../03-数据模型与数据库设计.md)保持一致。

## 实施状态与证据（2026-08-25）

- [`use-canvas-persistence`](../../lib/hooks/use-canvas-persistence.ts) 使用项目级单飞调度器：任何时刻最多一个持久化批次，批次期间产生的新 revision 在前一批确认后立即续传，失败项重新入队。
- [`outbox`](../../lib/canvas/outbox.ts) 将节点、边和 viewport mutation 按项目存入 IndexedDB；进入项目时先加载数据库快照，再重放 outbox，恢复在线后继续提交。IndexedDB 不可用会进入明确失败状态，不显示“已保存”。
- [`canvas-store`](../../stores/canvas-store.ts) 提供批量节点更新、在途/脏/待删集合、差异历史 patch 和服务端版本校正；undo/redo 继续走同一持久化管道。
- 媒体解析按 `assetId` 聚合并在到期前续签；并发续签使用 single-flight，同一资产的全部引用一次更新。工作台模型目录与脱敏凭据由 [`WorkbenchModelProvider`](../../lib/hooks/use-workbench-model-source.tsx)统一提供，节点数量不再放大请求。
- Playwright 固定生成 100、500、1,000 节点并记录交互耗时与请求数；结构门禁确认共享模型/凭据请求源不超过一个。性能结果作为当前机器基线，后续以相同浏览器和数据种子比较。

单飞、失败恢复、outbox、历史和媒体续签分别由 [`canvas-persistence.test.tsx`](../../tests/unit/canvas-persistence.test.tsx)、[`outbox.test.ts`](../../tests/unit/outbox.test.ts)、[`canvas-history.test.tsx`](../../tests/unit/canvas-history.test.tsx)和 [`canvas-media.test.tsx`](../../tests/unit/canvas-media.test.tsx)覆盖；离线刷新恢复与千节点场景由 Playwright 覆盖。

## 失败处理

| 场景                       | 处理                                                                           |
| -------------------------- | ------------------------------------------------------------------------------ |
| IndexedDB 不可用或配额不足 | 保持当前内存批次，立即显示不可离线恢复的错误；禁止显示“已保存”                 |
| 批次部分成功               | 按实体确认成功项，只恢复失败项；同一实体的新 revision 继续排队而不被旧响应清除 |
| 永久权限失败               | 停止发送该项目 outbox，拉服务端快照并提供冲突副本导出，不无限重试              |
| 页面崩溃或刷新             | 下次进入项目时先加载服务端快照，再按 revision 重放 outbox                      |
| undo/redo 持久化失败       | 界面保持撤销后的本地投影并标为未同步，允许重试；不偷偷重做以掩盖失败           |
| 签名 URL 续签失败          | 未到期时继续使用旧 URL；到期后显示可重试的媒体错误，不删除资产节点             |
| 批量更新包含无效节点       | 整批在本地校验阶段拒绝，避免产生部分历史和部分 outbox                          |

## 测试与验收

- Vitest 使用可控 Promise 证明任意时刻每个项目最多一个 flush，后产生的 revision 不会被旧响应确认或覆盖。
- 单元测试覆盖 upsert 合并、删除优先、失败 upsert 恢复、部分失败、重启重放、永久错误停止和指数退避。
- 浏览器测试在编辑后立即断网并刷新，恢复在线后数据库最终包含最后一次文本、位置、样式和边更改，界面状态依次为 offline、saving、saved。
- 撤销/重做覆盖文本、样式、旋转、边、删除和 50 节点批量移动；一次连续拖拽只产生一个历史条目并回到起始位置。
- 模拟签名 URL 到期与 401/403，续签只发起一次请求，所有相同 asset id 引用恢复显示。
- 1,000 节点时模型目录与凭据各只发起一次工作台级请求；单节点拖拽不触发媒体续签扫描。
- 性能报告固定浏览器版本、硬件、数据种子和动作脚本。与整改前相比，50 节点批量移动的 Store 更新次数由逐节点降为一次，网络写入按批次合并，功能测试全部保持通过。
