# 数据模型与数据库设计

## 一、设计原则

数据模型建立在 Supabase 的 PostgreSQL 之上，遵循四条原则。其一，**画布数据规范化为「一节点一行」**：画布上的每个元素是 `canvas_nodes` 表中的一行，而非把整块画布塞进单一 JSONB 字段，从而支持按节点的实时同步、增量持久化与未来的协作。其二，**真相唯一**：所有持久状态以数据库为唯一真相之源，客户端状态只是其投影，经 Realtime 校正。其三，**鉴权下沉**：每张业务表开启行级安全（RLS），权限即数据，客户端可安全直连。其四，**可配置优于硬编码**：模型清单等易变要素存于数据表，由数据驱动 UI，新增模型不改代码。

所有表统一具备 `id`（主键，UUID）、`created_at`（创建时间，带时区时间戳）两列；可变表另具 `updated_at`（更新时间，由触发器自动维护）。外键统一声明级联或置空策略以保证引用完整性。下文以表格描述每张表的字段，列含义为字段名、类型、约束与说明。

## 二、枚举

系统使用一组数据库枚举类型约束取值，避免脏数据并使语义自描述。`modality` 表示生成模态，取值为 image、video、text。`generation_status` 表示生成任务状态，取值为 pending（已创建待入队 / 待运行）、running（运行中）、succeeded（成功）、failed（失败）、cancelled（取消）。`message_role` 表示消息角色，取值为 user、assistant、system。`asset_kind` 表示资产种类，取值为 image、video。`asset_source` 表示资产来源，取值为 upload（用户上传）、generation（生成产出）。`node_type` 表示画布节点类型，取值为 image、text、shape、drawing、video、generation_placeholder、frame。

## 四、索引设计

索引按高频查询路径设计。`projects` 在（owner_id，is_deleted，updated_at 倒序）上建复合索引，服务「最近项目」的按主、过滤软删、按更新时间倒序的列表查询。`canvas_nodes` 在 project_id 上建索引，服务按项目整体加载画布；在（project_id，z_index）上建复合索引以便按层级取序；parent_id 上建索引以便取某画板的子节点。`canvas_edges` 在 project_id 上、并在 source_node_id 与 target_node_id 上分别建索引。`messages` 在（conversation_id，created_at）上建复合索引，服务会话历史的按序加载。`generations` 在 status 上建索引（轮询型任务按状态批量拉取运行中任务），在（project_id，created_at 倒序）上建复合索引，在 external_job_id 上建索引以便回调按外部任务号反查，idempotency_key 上的唯一约束兼作幂等去重索引。`assets` 在（owner_id，created_at 倒序）与（project_id）上分别建索引。`model_catalog` 在（is_active，sort_order）上建复合索引以驱动选择条。

## 五、行级安全策略

所有业务表开启 RLS，策略以「行归属于当前认证用户」为统一范式。

`profiles` 仅允许用户读写自身行（行 id 等于当前用户 id）。`projects` 允许用户对 owner_id 等于自身的行执行读、增、改；删除以软删除（置 is_deleted）表达，物理删除受限。`canvas_nodes`、`canvas_edges`、`conversations`、`messages`、`generations` 这些从属于项目的表，其策略统一表述为「该行所属项目的 owner 是当前用户」——即通过 project_id 关联到 projects 后校验归属，确保用户只能操作自己项目下的节点、边、会话、消息与生成任务。`assets` 允许用户读写 owner_id 等于自身的行。`model_catalog` 对所有已认证用户只读（仅返回 is_active 为真的行），写入仅限管理侧。

需要绕过 RLS 的服务端写入（如生成落库）由 Edge Function 以服务角色执行，且这些函数自行校验调用者身份与归属，绝不把服务角色密钥暴露给客户端。

## 六、Storage 存储桶与访问

设三个存储桶。`avatars` 存用户头像，读策略可设为公开或经签名访问，写入限本人。`uploads` 存用户上传的参考图与素材，私有，读写均限归属用户，客户端访问经签名 URL。`generations` 存生成产出的图片与视频，私有，读限归属用户、写入由 Edge Function 以服务角色完成。三桶的路径统一以用户标识为顶层前缀（形如「用户 id / 项目 id / 资产 id.扩展名」），既便于按用户隔离，也便于按项目清理。Storage 的访问策略与数据库 RLS 对齐，按 owner 隔离；图片资产借助 Storage 的图片变换能力在读取时即时生成缩略图，缩略图路径或变换参数记录于 `assets.thumbnail_path`；私有对象一律经短时效签名 URL 访问，分享场景另发可撤销的访问凭据。

## 七、节点数据结构

`canvas_nodes.data` 是一个随 `type` 变化的判别联合，承载各类型节点的差异化内容；通用的几何与层级信息（位置、尺寸、旋转、层级、父子）已提为独立列，`data` 只放类型私有内容。

图片节点（image）的 data 含图片的展示属性（如裁剪框、滤镜、透明度、圆角），真实媒体经 `asset_id` 关联 `assets`。文本节点（text）的 data 含文本串、字体族、字号、字重、行高、对齐、颜色、是否自动换行等排版属性。形状节点（shape）的 data 含形状种类（矩形 / 圆 / 多边形等）、填充色、描边色与宽度、圆角半径等。手绘节点（drawing）的 data 含路径点序列或归一化的矢量路径串、笔触颜色与宽度、平滑参数。视频节点（video）的 data 含封面帧、是否自动播放、是否静音、裁剪与播放区间，真实媒体经 `asset_id` 关联。生成占位节点（generation_placeholder）的 data 含展示用的提示词摘要与目标尺寸，经 `generation_id` 关联 `generations` 以追踪进度；任务完成后该节点被原地更新为对应的图片 / 视频节点（type 改写、asset_id 填入、data 替换）。画板节点（frame）的 data 含画板名、尺寸预设、背景，作为其他节点的可选父容器。这一判别联合在前端映射为 React Flow 节点的 `data`，详见第 06 篇的「数据库行与画布节点映射」。

## 八、数据库函数与触发器

为把贴近数据的逻辑沉到数据库，设若干函数与触发器，均以数据库逻辑表达、不在此展开代码。

**注册建档触发器**：监听 `auth.users` 的插入，自动在 `profiles` 为新用户建行。

**更新时间触发器**：在各可变表（profiles、projects、canvas_nodes、conversations、generations 等）的更新前自动刷新其 `updated_at`。

**项目活跃度触发器**：在 `canvas_nodes`、`canvas_edges`、`messages` 发生变更时，刷新所属 `projects.updated_at`，使「最近项目」排序实时反映活跃度。

**占位转化逻辑**：生成成功后把占位节点更新为真实节点的写入逻辑，置于 Edge Function（结果落库流程）中执行，而非数据库触发器，以便与 Storage 写入、资产建档协同；数据库侧仅保证这组写入处于同一事务以维持一致。

是否使用 Database Webhooks 把「生成任务插入」转交 Edge Function、是否使用 Supabase Queues 承载待处理任务，由第 05 篇的流水线设计统一约定；数据库侧据其约定开启相应发布与队列。

## 九、Realtime 发布配置

为支撑实时回流，将 `canvas_nodes`、`canvas_edges`、`generations` 三张表纳入 Realtime 发布，向订阅了对应项目频道的客户端推送其行的插入、更新、删除变更。这三张表设置完整的副本标识（replica identity full）以便变更事件携带足够的旧值 / 新值供客户端做精确的局部更新。`messages` 表可按需纳入发布以支持对话流的实时追加（同一用户多设备场景）。其余表（profiles 等）不纳入实时发布。Realtime 的频道访问同样受授权约束，客户端只能订阅自己有权访问的项目频道。

## 十、数据生命周期

项目删除采用软删除（置 is_deleted），在「最近项目」中即时隐藏，保留一段保留期供恢复，保留期后由定时任务物理清理项目及其级联的画布节点、边、会话、消息、生成任务。资产清理遵循「孤儿回收」：定时任务扫描既不被任何画布节点引用、也不被任何消息附件引用、且超过保留期的资产，删除其 Storage 对象与数据库记录，避免存储膨胀。生成任务的中间态有超时保护：长时间停留在 running 且无进度推进的任务被定时任务判定超时、置为 failed。所有清理任务经 pg_cron 调度，删除前确保级联与外键策略不致破坏引用完整性。
